# NextDevTpl 3.x 到 4.0.0 升级指南

> 适用范围：由 `create-nextdevtpl` 生成并已独立维护的应用
>
> 稳定接口与版本边界：[M6 - 兼容性与稳定版](模块设计/兼容性与稳定性.md)

生成项目归使用方维护。NextDevTpl 4.0.0 不会覆盖现有项目，也没有自动原地升级命令。建议先在临时目录用相同选择生成新项目，再审查差异并手工分批合并。

## 3.x 与 4.0.0 的主要变化

| 方面 | 3.x 项目 | 4.0.0 对照项目 |
| --- | --- | --- |
| 产品页面 | 直接维护生成项目中的应用页面 | 页面视图由生成时选定的皮肤提供，运行时仍是一套固定皮肤 |
| 运行模式记录 | 生成记录没有 `mode` | 完整模式记录 `mode: "full"`；旧缺省仍解释为完整模式 |
| 皮肤记录 | 可能没有皮肤来源信息 | 记录皮肤编号、版本、包摘要和来源类型；可包含配色摘要 |
| 演示模式 | 没有面向纯前端评估的固定组合 | 可单独生成 `mode: "demo"`；它是展示用途的新应用，不是现有生产项目的升级目标 |
| 套餐配置 | 金额和权益可能散落在应用配置中 | 完整支付配置和皮肤定价展示从 `src/core/plans/` 派生 |
| 皮肤接口 | 无 | `skin.json` 声明模板兼容范围、`viewApi`、模块、视图入口、素材和文件摘要 |

迁移时以 4.0.0 生成结果为对照，不要把这张表当作自动迁移清单。实际改动以你的 3.x 生成记录、应用差异和 4.0.0 发布说明为准。

## 升级前准备

1. 提交或备份当前代码，确认可以恢复到升级前状态。
2. 备份数据库，记录数据库类型、迁移编号、部署目标和 Node/pnpm 版本。
3. 保留 `nextdevtpl.generated.json`。旧记录记下预设、模块、适配器、目标和 catalog 版本。
4. 单独保存该记录未包含的信息：远端皮肤 URL、远端包 SHA-256、令牌密钥的来源、本地皮肤目录、StyleKit 配色编号，以及项目自行修改的页面和服务。
5. 运行当前项目原有的类型、测试、构建和健康检查，保存基线结果。

生成记录刻意不包含远端 URL、令牌值或本地绝对路径。不要把这些值补写进生成记录后提交到应用仓库；通过团队密钥管理和升级记录保存。

## 生成对照项目

根据旧 `nextdevtpl.generated.json` 手工翻译 CLI 参数。不要对现有目录运行生成器。

```bash
pnpm dlx create-nextdevtpl@4.0.0 ../nextdevtpl-v4-compare \
  --preset custom \
  --modules auth,dashboard,support \
  --target server \
  --payment stripe \
  --skin ./my-skin \
  --no-install --yes
```

示例中的预设、模块、适配器、目标和皮肤都需要替换为当前项目实际选择。省略 `--skin` 使用内置默认皮肤。需要配色时只可使用内置默认皮肤，例如：

```bash
pnpm dlx create-nextdevtpl@4.0.0 ../nextdevtpl-v4-compare \
  --preset saas \
  --target vercel \
  --skin default \
  --palette glassmorphism \
  --no-install --yes
```

完整模式是默认模式。旧记录没有 `mode` 时按 `full` 解释。只有在新建独立演示项目时才使用 `--mode demo`；demo 只支持 `server`，拒绝显式预设、模块和服务适配器，也不包含数据库、业务 API 或业务环境变量。

## 逐项比较

在临时目录生成新项目后，先比较生成记录，再比较代码：

- 生成记录新增的 `mode`、`skin`、`palette` 和 demo 数据摘要字段。
- `src/skin/` 下的令牌、字体、布局、视图和基础 UI 覆盖。
- `src/core/skin/` 下的固定页面出口、视图类型和完整/演示控制器边界。
- `src/core/plans/` 与原支付配置：确认计划金额、积分额度、文件限制和权益键与原项目相同。
- `src/features/*/view/contracts.ts` 和皮肤页面：将自己的视图修改迁入皮肤，不依赖 `src/core/skin/demo/` 私有实现。
- `package.json`、锁文件、`messages/`、`.env.example`、部署配置和相关测试。
- Drizzle schema 与迁移：确认是否确有数据库变更，再决定要不要迁移。

如果旧项目改过默认页面，先明确哪些属于自己的产品设计，再把改动移到本地皮肤或应用业务代码。升级时不要无差别覆盖现有视图，也不要把新皮肤文档准备目录作为生成项目依赖。

## 皮肤与配色迁移

4.0.0 的皮肤在生成时选定。新建对照项目时，可先使用 `--skin default`，再将自定义视图迁入符合 `skin.json` 的本地皮肤。检查清单中的 `compatibility.template` 与 `compatibility.viewApi`，模块声明、视图编号、依赖和素材文件都要匹配。

如果使用远端皮肤，保存 HTTPS 归档地址和 SHA-256；URL 和访问令牌不会出现在生成记录里。若原项目使用 StyleKit 配色，重新生成时显式传入 `--palette <slug>`；当前只有内置默认皮肤支持配色，生成器使用包内 149 项离线快照并为选定配色附带 MIT 许可文件。

新生成记录的 `skin.source` 只记录来源类型：远端来源保留归档摘要，本地来源不保留目录路径。请把再次生成所需的来源信息放在适当的团队配置中，避免将令牌写入命令历史或项目清单。

## 数据库迁移

4.0.0 完整模式保留所选数据库能力。检查对照项目与当前项目的 Drizzle schema、迁移和适配器配置：

1. 只合并当前应用需要的 schema 及迁移。
2. 通过 `pnpm db:generate` 生成新的向前迁移，并审阅 SQL。
3. 在临时或测试数据库执行迁移，检查现有业务数据和回退策略。
4. 在完整环境通过迁移、类型、测试、生产构建和服务健康检查后再安排生产窗口。

不要删除、重写或回滚已经在生产执行的迁移。demo 导出没有数据库；不要把 demo 脚本或环境变量套用到生产完整项目。

## 人工合并与验收

按“工具链与依赖、皮肤和视图类型、业务模块、数据库、外部服务、部署配置”的顺序分批合并。每批记录选择和影响，并运行相关检查。最终至少覆盖：

- 完整模式登录、核心业务流程、支付或其他选定服务、迁移及部署健康检查。
- 皮肤的中英文、浅色/深色、桌面/手机页面，长文本、空状态、加载态和错误态。
- 如需交付 demo，单独检查无业务环境变量安装、普通 Next 软导航、内存状态跨路由保留和刷新复位；不把 UI 操作当成真实账号或交易。
- 全部新旧差异与数据库变更都经过代码审查，并保存验证结果。

## 回退

应用代码回到升级前的提交。已经在生产执行的数据库迁移用独立审核的向前修复迁移处理，不删除迁移历史或生产数据。按部署记录恢复服务凭证和外部配置。
