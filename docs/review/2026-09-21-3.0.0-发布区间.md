## P1 问题

### P1-028 用户改过一次套餐后，订阅续费历史永久不再记录

状态：待修复。

- 位置：`src/app/api/webhooks/payment/route.ts:781-880`
- 触发：用户在站内做过一次升级或降级（`subscription_history` 留下一条 `sourceType=action` 的 `upgrade_requested` / `downgrade_requested`），之后该订阅的每一次自然续费 Webhook。
- 影响：`requestedChange` 查询只按订阅、来源和目标价格匹配，没有任何时间窗口或「是否已确认」的限制，所以那条历史请求记录会被后续每一次 Webhook 重新命中。续费时 `existing.priceId === resolved.priceId`，流程进入 `else if (requestedChange && requestedCorrelationId)` 分支，用同一个 correlation ID 再写一次 `*_confirmed`；这条记录被 `subscription_history_correlation_event_unique` 挡下并由 `onConflictDoNothing()` 静默吞掉，而第三个分支的 `renewed` 已经没有机会执行。结果是订阅历史从此再也记不到任何续费事实。
- 附带影响：降级场景下，供应商在动作发生时就会先发一次 `subscription.updated`，此时已写入 `downgrade_confirmed`；等到下个周期降级真正生效、价格发生切换时，同样因为 correlation ID 冲突写不进去，「降级实际生效」这条事实也一起丢失。
- 证据：`recordSubscriptionHistory` 使用无目标的 `onConflictDoNothing()`；唯一索引为 `(event_type, correlation_id)`；`requestedChange` 查询无 `createdAt` 下界，也不排除已存在确认记录的请求。积分发放和收入入账走独立幂等键，不受影响，所以这是纯粹的审计链路缺口。
- 修复方向：命中 `requestedChange` 后先确认是否已有同 correlation ID 的确认记录，已确认就让流程继续走续费判定；或者给请求查询加上「晚于上一周期开始时间」的下界，让历史请求不再拦截后续周期的事件。

## P2 问题

### P2-019 取消订阅失败时前端提示成功，并丢掉重试用的幂等请求 ID

状态：待修复。

- 位置：`src/features/settings/components/billing-section.tsx:129-143`、`src/lib/safe-action.ts:32-45`
- 触发：取消订阅时后端抛错（没有可取消的订阅、供应商请求失败、事务回滚等）。
- 影响：`handleServerError` 把异常转成 `serverError` 字符串返回，动作本身不会抛出，所以 `try/catch` 永远不进 `catch`。代码继续执行：清空 `cancelRequestIdRef`、关闭对话框、弹出「取消成功」。用户看到成功提示但订阅没有被取消；再次点击时生成全新的 `requestId`，既绕过 Action 内的重放判定，也让供应商侧的 `Idempotency-Key` 失去作用。
- 证据：同一提交里的 `src/features/marketing/components/pricing-section.tsx:204-226` 是正确写法——先判断 `result?.data?.success`，失败时保留 ref 并提示失败。
- 修复方向：按 pricing-section 的写法检查返回值，失败时保留 `cancelRequestIdRef` 并走失败提示。

### P2-020 埋点不符合契约时静默丢弃，没有任何日志

状态：待修复。

- 位置：`src/core/services/telemetry.ts:614-631`、`src/services/telemetry.ts:41-45`
- 触发：事件名、版本、来源或属性任一项不满足 `telemetryEventRegistry` 的登记。
- 影响：`createTelemetryEvent` 在 `track()` 内部抛出 ZodError，位置在包住适配器调用的 `try/catch` 之外，最终被 `trackServerEvent` 的空 `catch` 吃掉。`onAdapterError` 只覆盖适配器投递失败，覆盖不到契约校验失败。开发者改了属性之后，事件会在生产环境无声消失，没有任何排查线索。
- 修复方向：把契约校验失败单独捕获并按降级错误上报（复用 `onAdapterError` 或新增一个回调），保证「事件被拒绝」这件事本身可观测。

### P2-021 游客一次性支付的 `payment.checkout.completed` 埋点必然被丢弃

状态：待修复。

- 位置：`src/adapters/payment/stripe.ts:153-180`、`src/app/api/webhooks/payment/route.ts:308-322`、`src/core/services/telemetry.ts` 事件登记
- 触发：Stripe `mode=payment` 且没有创建客户对象的 Checkout 完成。
- 影响：`mapCheckout` 在拿不到客户时回落成 `customerId: ""`，拿不到商品时回落成 `productId: ""`，而事件登记要求这两个字段至少 1 个字符。校验不通过，整条转化事件被丢弃；叠加 P2-020 之后完全无感知。同一路径的 `data.customer.id` 在写库前还有 `if (data.customer.id)` 判空，说明空值确实会出现。
- 修复方向：适配器不要用空字符串占位，拿不到就不给该字段；对应事件把 `customerId` 调整为可选，或在发送前补齐来源。

### P2-022 补差价收入的价格 ID 可能记成旧套餐价格

状态：待修复。

- 位置：`src/adapters/payment/stripe.ts:124-146`
- 触发：站内升级触发 `proration_behavior=always_invoice`，Stripe 回传 `billing_reason=subscription_update` 的补差价 invoice。
- 影响：`mapInvoice` 取 `lines.data[0].price.id` 作为 `productId`，而补差价 invoice 的第一行通常是旧价格的未使用时长冲抵行，新价格的补收行排在后面。落库的 `revenue_event.price_id` 因此指向旧套餐，`interval` 也跟着按旧价格配置回填。金额本身取 `amount_paid`，是净额，没有问题；受影响的只有按价格维度的归因。
- 修复方向：优先取金额为正的那一行，或取与订阅当前价格一致的行；都取不到就不写 `price_id`，不要让错误归因伪装成确定值。

### P2-023 重复点击已挂起的降级会反复写入降级请求历史

状态：待修复。

- 位置：`src/features/payment/actions.ts:359-376`
- 触发：已经存在待生效降级的用户，再次点击同一个降级目标。
- 影响：这条分支不调供应商直接返回，但每次都会写一条 `downgrade_requested`。前端每次重新点击会生成新的 `requestId`，`(source_type, source_event_id)` 和 `(event_type, correlation_id)` 两个唯一索引都拦不住，订阅历史被同一次降级的重复请求撑大。
- 修复方向：进入该分支前先查有没有同订阅、同目标价格且未确认的降级请求，有就直接复用它的 correlation ID 返回，不再新增记录。

### P2-024 catalog 的事件归属既没有同步校验，也没有被生成器使用

状态：待修复。

- 位置：`recipes/catalog.json`、`packages/create-nextdevtpl/src/catalog.ts:61-76`、`src/test/architecture/generator-catalog.test.ts:22-29`
- 触发：新增或调整模块事件归属时只改一侧。
- 影响：catalog 的 `telemetryEvents` 是必填字段（缺失会导致解析报错），但解析出来之后没有任何地方读取它，生成器不会据此裁剪或校验；同步测试只比对 `dependencies` 和 `translations`，不比对 `telemetryEvents`（`schema`、`routes` 同样没比对）。两边当前恰好一致，但可以无声漂移。文档里写的「单元测试每个事件的必填属性、可选属性、禁止属性、版本和来源」也只覆盖了少数几个事件。
- 修复方向：在同步测试里补上 `telemetryEvents` 的逐模块比对；要么让生成器真正使用这个字段，要么明确它只是清单元数据并在文档中说清楚。

### P2-025 `subscription.activated` 已登记并归属模块，但没有任何代码发送

状态：待修复。

- 位置：`src/core/services/telemetry.ts:472-476`、`src/features/subscription/manifest.ts:13`
- 影响：模块清单校验只拒绝「未登记事件」和「重复归属」，不要求登记的事件真的被发送，所以这条空属性事件是个永远不会出现的幽灵事件。订阅激活的实际埋点走的是 `payment.subscription.created`。
- 修复方向：要么补上发送点，要么从注册表和模块清单中一起删掉。

## 其他观察（不单独立项）
