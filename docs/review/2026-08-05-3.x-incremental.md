## P1 问题

### P1-020 Telemetry 身份在分析同意前已创建并继续传播

状态：已解决（本轮修复）。

修复：身份初始化、认证请求头和撤回清理共用分析同意门禁；未选择真实分析适配器的生成项目不挂载身份 Provider。

- 位置：`src/lib/telemetry/identity-provider.tsx:7-10`、`src/lib/telemetry/identity.ts:334-365`、`src/lib/auth/client.ts:22-29`、`src/app/[locale]/layout.tsx:71-79`、`packages/create-nextdevtpl/src/generate.ts:774-815`
- 触发：用户尚未同意分析、选择拒绝分析，或生成项目选择 `analytics:noop`/没有分析同意 UI 时，页面挂载 `TelemetryIdentityProvider` 或发起 Better Auth 请求。
- 影响：匿名 ID 和归因值会在同意前写入 Cookie/localStorage，并通过认证请求头进入服务端事件上下文；用户撤回同意后，旧身份仍会被继续带上。当前 GA 组件的同意处理无法覆盖这条身份链路，违反 Cookie 政策和 operations 文档中“同意后开始采集”的承诺。
- 证据：`initializeTelemetryIdentity()` 无同意检查，`getClientTelemetryHeaders()` 每次认证请求都会初始化并读取身份；身份 Provider 在根布局中无条件挂载。已解决的首轮 `P1-016` 只处理 GA runtime 和 GA Cookie，未覆盖这条自有 telemetry 身份链路。
- 修复方向：让身份创建、header 注入和撤回清理共用 analytics consent gate；拒绝或撤回时删除匿名 ID、归因 Cookie 和 localStorage。生成项目也应在没有可用同意入口时禁止初始化可选分析身份。

### P1-021 运营统计时区只被回显，实际查询仍按 UTC 切日

状态：已解决（本轮修复）。

修复：查询窗口和每日快照按 IANA 时区计算本地日边界，快照日期与窗口使用同一时区转换。

- 位置：`src/features/operations/repository.ts:46-64`、`src/features/operations/snapshot.ts:9-28`、`src/test/operations/metrics.test.ts:32-40`
- 触发：传入 `timezone: "Asia/Shanghai"` 等非 UTC 时区，或在本地午夜附近查看周期指标和每日快照。
- 影响：`getOperationsPeriod()` 固定以 UTC 计算 `start/end`，只把传入时区写入返回值；快照日期也从 UTC 的 `period.start` 截取。管理员看到的时区标签与数据边界不一致，跨日数据会被放入错误日期，多个时区生成的快照还可能保存相同数据。
- 证据：运营驾驶舱设计要求统计时区可由管理员选择，当前测试反而把非 UTC 输入固定断言为 UTC 边界。
- 修复方向：按 IANA 时区计算本地日的 UTC 起止时间，并让快照日期、查询窗口和对比周期使用同一套时区转换；补充夏令时和跨日测试。

### P1-022 AI 成本聚合用报告期结束时间定价历史请求

状态：已解决（本轮修复）。

修复：保留 `ai_usage_event.occurredAt`，按每条 AI 请求发生时间选择价格版本后再聚合成本。

- 位置：`src/features/operations/repository.ts:183-194`、`src/features/operations/ai-usage.ts:65-90`
- 触发：一个报告期内存在价格版本变化，且该期包含价格生效前后的 AI 请求。
- 影响：所有请求都把 `period.end` 传给 `estimateAICost()`，早期请求会按报告期末价格计算，AI 成本和毛利会偏高或偏低。
- 证据：价格查找函数支持按 `occurredAt` 选择生效版本，AI 成本模块文档明确要求历史请求使用当时有效价格，但聚合时没有使用 `aiUsageEvent.occurredAt`。
- 修复方向：保留每条查询行的 `occurredAt`，按事件发生时间估算成本后再聚合，并增加跨价格版本的 repository 测试。

### P1-023 付费转化率把续费当首购，且分子分母不是同一用户 cohort

状态：待修复。

- 位置：`src/features/operations/repository.ts:95-100`、`src/features/operations/repository.ts:120-172`、`src/content/docs/zh/operations.mdx:58-60`
- 触发：报告期内发生订阅续费、补单，或用户在报告期之前注册、报告期内付款。
- 影响：`payment_succeeded` 包含订阅创建和每次续费，`paidUsers` 会把续费用户当成周期付费用户；分母却只统计周期内新注册用户。老用户续费可以进入分子但不进入分母，转化率可能虚高甚至超过 100%，也不能代表首次有效订阅转化。
- 证据：`handleSubscriptionRenewed()` 每个周期写入 `payment_succeeded`，运营查询只按用户去重，没有判断首次有效订阅；文档定义为周期内去重付费用户/注册用户，当前实现仍混入续费事实。
- 修复方向：从订阅生命周期或首个有效订阅事实计算首购 cohort，明确分子分母的时间范围；续费只用于收入和留存相关指标。

### P1-024 告警状态读改写非原子，并发任务会重复发送或失败

状态：已解决（本轮修复）。

修复：告警状态使用事务行锁，首次建档和 delivery 使用冲突忽略与稳定 ID；通知发送放在事务外，单条规则失败不阻断后续规则。

- 位置：`src/features/operations/alerts/repository.ts:51-119`、`src/db/schema/operations.ts:49-83`
- 触发：两次告警 cron 重叠运行，或同一规则的两个实例同时处理同一个 `dedupeKey`。
- 影响：两个实例可能读到同一个旧状态并都发送通知，造成重复邮件/Webhook；首次创建时还可能因唯一索引冲突让整次任务返回 500，后续规则不再处理。
- 证据：代码先 `select`，再 `update/insert`，随后发送通知和写 delivery；`dedupeKey` 虽有唯一索引，却没有事务锁、原子 upsert 或 delivery 级幂等键。
- 修复方向：用事务和行锁/原子 upsert 领取状态，再用稳定 delivery key 防重复发送；单条规则失败不能中断后续规则。

### P1-025 旧周期订阅 Webhook 被忽略状态更新，却仍会入账收入

状态：已解决（本轮修复）。

修复：只有 `createOrUpdateSubscription()` 接受当前事件时，checkout、激活和续费分支才写周期收入事实。

- 位置：`src/app/api/webhooks/payment/route.ts:503-523`、`src/app/api/webhooks/payment/route.ts:651-677`、`src/app/api/webhooks/payment/route.ts:597-603`
- 触发：新周期订阅事件已先处理，旧周期的 `subscription.active` 或 `subscription.renewed` 事件随后迟到或被重放。
- 影响：`createOrUpdateSubscription()` 返回 `applied: false` 后，处理函数仍无条件调用 `recordRevenueEvent()`；旧周期的事件 ID 会形成新的收入键，运营收入和付费用户数被重复或倒灌。
- 证据：状态更新分支明确记录并忽略 stale event，但收入记录没有使用 `applied` 结果做保护。
- 修复方向：只有事件被采纳时才执行周期收入履约；或者采用供应商交易级外部 ID 入账，并把 stale event 在收入入口前单独挡住。

### P1-026 立即升级的补差价没有进入收入读模型

状态：待修复。

- 位置：`src/features/payment/actions.ts:342-402`、`src/app/api/webhooks/payment/route.ts:488-523`、`src/features/payment/revenue.ts:31-56`
- 触发：用户在当前计费周期内升级，Action 请求 `proration-charge-immediately`，供应商随后发送订阅更新事件。
- 影响：升级补差价没有独立交易金额和交易 ID；订阅更新仍用 `subscriptionId + currentPeriodStart` 作为周期收入键，并从本地 `priceId` 目录价推导金额。若当前周期已有收入，补差价会被幂等键吞掉；即使新写入，也可能记成目录价而非真实扣款。
- 证据：`PaymentSubscription` 契约不携带账单金额，升级 Action 也没有写 `revenue_event`；Stripe 的订阅更新映射只提供订阅状态和周期。
- 修复方向：接入供应商的 invoice/payment 事实，按交易级 ID 和真实 `amountMinor` 记录补差价；周期订阅收入与升级调整分开建模。

### P1-027 Cloudflare 远端预检漏掉 operations 的 `CRON_SECRET`

状态：已解决（本轮修复）。

修复：静态预检和生成项目在选择 `operations` 或 `credits` 时都把 `CRON_SECRET` 纳入远端 Secret 检查。

- 位置：`cloudflare/preflight-config.json:30-40`、`packages/create-nextdevtpl/src/generate.ts:327-331`、`src/app/api/jobs/operations/snapshot/route.ts:7-20`、`src/app/api/jobs/operations/alerts/route.ts:7-25`
- 触发：启用 `operations` 的 Cloudflare 项目没有把 `CRON_SECRET` 写入 Wrangler 远端 Secret，仅配置了本地环境变量或普通变量。
- 影响：`cf:deploy` 的远端 Secret 检查可以通过，但线上两个 operations cron 路由因缺少 `CRON_SECRET` 永远返回 401，日快照和告警不会运行。
- 证据：静态预检的 `required` 包含 `CRON_SECRET`，`remoteRequired` 没有；生成器只在选择 `credits` 时加入远端检查，operations 选择没有对应分支。两个路由都在缺少 secret 时直接拒绝请求。
- 修复方向：按模块/路由元数据汇总远端 Secret，把 operations 的 cron 密钥加入 generated 和静态预检；补充缺少远端 Secret 时的预检测试。

### P2-012 MRR 把 trialing 订阅计入有效经常性收入

状态：已解决（本轮修复）。

修复：MRR 查询只读取 `active` 订阅，试用状态不再计入经常性收入。

- 位置：`src/features/operations/repository.ts:120-166`、`src/features/operations/revenue.ts:58-61`
- 触发：存在 `trialing` 状态的订阅。
- 影响：试用期通常尚未产生付费收入，但查询把 `active` 和 `trialing` 一起按套餐价格折算 MRR，运营面板会高估经常性收入。
- 证据：收入与订阅健康文档明确要求 MRR 只统计有效经常性订阅。
- 修复方向：只纳入已付费且当前生效的订阅；如产品确实要展示试用价值，单独增加试用指标，不混入 MRR。

### P2-013 任一运营数据源失败会让整页失败，无法返回 partial/query-failed 指标状态

状态：已解决（本轮修复）。

修复：运营查询按数据源独立收敛错误，受影响指标返回 `query-failed`，其余指标继续返回；收入、漏斗和 AI 毛利组合指标同步标记依赖失败。

- 位置：`src/features/operations/repository.ts:67-158`、`src/app/[locale]/(admin)/admin/operations/page.tsx:16-22`、`src/features/operations/types.ts:1-14`
- 触发：用户、订阅、积分、工单、收入或 AI 查询中的任一 Promise 失败。
- 影响：`Promise.all` 直接拒绝，页面只显示通用错误；其他查询本来可用的数据也不会展示，类型中声明的 `partial` 和 `query-failed` 没有按指标落地。
- 证据：模块设计文档要求完整、空、部分和失败查询都有明确状态，页面当前只对整个 dashboard 做 `.catch(() => null)`。
- 修复方向：按数据源隔离查询错误，给受影响指标写 `query-failed`，其余指标保留；跨源组合结果标记 `partial` 并携带来源和原因。

### P2-014 告警尚未真正发送时就可能产生恢复通知

状态：已解决（本轮修复）。

修复：恢复通知增加成功 firing delivery 门槛，未达到连续触发或发送失败后恢复都不会发送恢复消息。

- 位置：`src/features/operations/alerts/state.ts:22-50`、`src/features/operations/alerts/repository.ts:101-119`
- 触发：规则要求连续两次命中，第一次命中后内部状态已写成 `firing` 但没有发送通知，下一次评估前指标恢复。
- 影响：状态机只看 `previousStatus === "firing"`，会发出孤立的“已恢复”消息，历史看起来像发生过一次已通知的告警。
- 证据：首次未达到连续次数也会返回 `status: "firing"`；恢复分支只检查状态，没有检查是否存在成功的 firing delivery。
- 修复方向：区分“内部观察状态”和“已发出告警状态”，恢复通知前确认有成功的 firing delivery。

### P2-015 订阅 Action 与 Webhook 会重复写同一生命周期历史

状态：待修复。

### P2-018 公开 telemetry 接口没有限流或来源保护

状态：已解决（本轮修复）。

修复：新增 telemetry 独立限流、16 KiB 请求体上限、流式读取限制和可选同源校验。

- 位置：`src/app/api/telemetry/route.ts:13-56`、`src/middleware.ts:25-33,65-90`
- 触发：外部脚本或手工请求直接 POST `/api/telemetry`；该路由无需登录，也没有进入 API 限流白名单。
- 影响：攻击者可以伪造事件污染漏斗和运营指标；选择了付费分析供应商时还可以刷高外部请求量。请求体只经过结构校验，没有按 IP/匿名身份限流或总大小限制。
