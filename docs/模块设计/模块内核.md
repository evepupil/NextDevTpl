## 职责与边界

内核只定义稳定的数据契约和校验规则，不读取任何业务模块。认证、支付、积分、
工单等业务能力各自维护公开入口和模块声明；组合层负责选择并注册模块，页面、
API 和其他模块只能通过公开入口使用它们。默认公开入口为模块根目录的
`index.ts`；需要隔离客户端、服务端加载边界时，可以提供命名入口，包括
`actions`、`components`、`config`、`server`、`types`、`utils`；4.x 增加客户端安全的
`view` 入口，服务端查询仍由 `server` 暴露。

M1 负责建立可执行的模块边界和组合信息，不改变现有产品功能，也不引入新的
供应商抽象。支付、存储、邮件等供应商适配将在 M2 处理，源码生成和物理删除
将在 M3 使用本阶段产出的模块清单。

## 结构与数据流

```text
src/core/modules/contract.ts       模块声明类型与纯校验函数
          ^
          | 只依赖稳定契约
src/features/*/manifest.ts         各模块声明依赖、路由、菜单、翻译和 Schema
          ^
          | 由组合入口显式注册
src/modules/registry.ts            完整模板的模块注册表
          |
          +-> src/config/nav.ts    组合 Dashboard / Admin 菜单
          +-> 架构测试             检查依赖、公开入口和翻译命名空间

src/db/schema/*.ts                 按模块维护表结构
src/db/schema/index.ts             Drizzle 使用的统一 Schema 出口
```

页面或 API 的调用方向固定为：入口 -> 模块公开 API -> 模块内部实现 -> 数据库
或外部服务。模块内部可以深层引用自身文件；跨模块调用和 `src/app/` 等外部入口
必须使用 `@/features/<模块>`。服务端代码需要避开混合入口造成的加载环时，
可以使用模块声明的命名公共入口。

## 模块声明

每个模块通过纯数据声明以下信息：

- `id`、类型和说明；
- 直接依赖的其他模块；
- 拥有的页面与 API 路由；
- Dashboard 或 Admin 菜单贡献；
- 使用的翻译顶层命名空间；
- 需要聚合的数据库 Schema 分组。
- 标准遥测事件；4.x M1 增加可选视图编号与种类。

注册表校验模块 ID、依赖存在性、循环依赖、重复路由和重复菜单地址。M3 可以
基于同一份声明计算选中模块的依赖闭包，并删除未选模块拥有的路由和 Schema。

## 关键决策

- 保持 Server Components、Server Actions 和 App Router 的现有使用方式。
- `src/core/` 永远不导入 `src/features/`；完整模板的组合入口放在
  `src/modules/`。
- 模块公开能力默认从 `index.ts` 导出；需要控制打包边界时，可以按职责使用
  `actions`、`components`、`config`、`server`、`types` 和 `utils` 命名入口。
  架构测试只允许根入口、这些命名入口及注册表使用的 `manifest`，并拦截其他
  跨模块深层导入。
- 邮件模块的认证集成只使用 `mail/server`，避免 Newsletter Action 经
  `safe-action` 反向加载认证配置形成循环依赖。
- 支付与订阅模块的客户端、Edge 和服务端调用使用对应命名入口，防止根入口把
  Node 数据库驱动或 `node:crypto` 带入浏览器及 Edge 构建。
- Schema 按认证、订阅、积分、邮件和工单拆分，表名、字段和迁移结果保持不变。
- 菜单由模块声明组合；图标映射留在展示配置层，核心契约只保存图标名称。
- 翻译文件本阶段继续保留中英文总文件，模块声明负责登记命名空间并检查两种
  语言都存在。M3 生成项目时再按登记结果裁剪 JSON。
- App Router 路由暂不搬动，模块声明记录文件归属，供 M3 生成器执行删除。

## 当前实现

- `src/core/modules/` 定义 16 个模块 ID、声明契约、注册校验和依赖闭包计算；
  核心模块不能依赖可选模块。
- 每个 feature 都有独立 manifest，登记直接依赖、路由、菜单、翻译命名空间和
  Schema 所有权；`src/modules/` 提供完整注册表、预设和源码选择结果。
- 管理后台首页、用户管理、工单管理路由与 Admin 导航归属 `admin`；工单数据和动作仍
  归属 `support`，由 `admin` 依赖 `support` 提供实现。仅选 `support` 时不保留管理后台路由组。
- `minimal` 预设选择认证与 Dashboard，依赖闭包稳定为 `auth`、`dashboard`、
  `mail`、`shared`，并能列出需排除的可选模块及其路由。
- Dashboard 和 Admin 菜单由模块声明组合；工作区按能力开关挂载积分与套餐徽标，
  经生成的控制入口取数，可选模块移除后不需要修改侧栏视觉代码。
- 数据库 Schema 已按认证、订阅、积分、邮件和工单拆分，原 `schema.ts` 保留
  兼容导出，Drizzle 使用聚合入口；拆分前后的 49 个导出保持一致。
- 页面、API 和跨 feature 调用已切换到公开入口；架构测试检查未声明依赖、
  非公开深层导入、路由源码、菜单地址和中英文翻译命名空间。
- `/dashboard/credits` 已补充兼容路由并跳转到用量设置页，模块菜单不再指向
  404 页面；Open Graph 模板移到不属于任何业务 feature 的 SEO 公共组件。

### 4.x 视图扩展

公共 `ModuleViewDefinition` 与可选 `ModuleManifest.views` 已建立，编号以拥有模块加点号
开头，种类为 `page`、`layout` 或 `component`。格式、归属、重复校验和选择汇总已实现，清单与 recipe 的
一致性由独立测试核对。
各 feature 维护自己的参数与控制接口，组合层生成所选视图映射；核心只定义通用的类型与纯
校验，不反向导入任何 feature 或默认皮肤。具体编号、路径及约定见[视图契约](视图契约.md)。

控制台外壳及原有无积分回退归属 shared，确保未选 dashboard 的组合也能保留基础外壳；
控制台实际首页仍归属 dashboard。积分、订阅和认证通过组合层按选择接入，不成为基础模块
的静态依赖。

工作区只在原有条件下挂载可选控制器：用户信息出现后获取余额、账号弹出菜单打开后获取套餐。
`Dashboard`、`DashboardPages` 和通用 `Subscription` 徽标文案由 shared 登记，未选 dashboard
或 subscription 时，保留的公共视图不会引用已裁剪的翻译。M2 视图数量为 20 项，其中包含 15 个
页面、3 个外壳、1 个兼容首页回退和 1 个营销页头；两个积分入口继续重定向。页头增加明确的
组件登记，供文档站复用所选皮肤；文档站整体布局继续由核心维护。

## 验证方式

- 模块注册表测试：ID、依赖、循环、路由、菜单、Schema 和翻译登记。
- 源码边界测试：禁止跨模块深层导入，禁止依赖未声明的业务模块。
- 最小集合测试：验证基础模块的依赖闭包不包含可选业务模块。
- Schema 回归：Drizzle 聚合出口保持原有表和类型，并运行现有数据库测试。
- 项目门禁：format、lint、typecheck、283 项测试和生产构建。

2026-07-23 最终验证结果：Biome 格式化与 lint 通过，TypeScript 严格类型检查
通过，16 个测试文件的 283 项测试全部通过，Next.js 生产构建通过并完成 87 个
页面条目的生成检查。实现提交为 `30a71b5`。
