> 模块定位：从服务端业务事实计算收入、付费转化和订阅健康指标

## 职责与边界

本模块负责建立可审计的支付与订阅读模型，并向运营驾驶舱提供收入指标。它不承担
正式会计记账，也不使用浏览器埋点确认收入。

## 结构与数据流

```text
Creem / Stripe Webhook -> 规范化支付事件 -> 订阅读模型 -> 收入指标
                                      \-> 产品分析事件（用户路径）

价格页 -> 计划变更 Action -> Creem / Stripe
账单页 -> 订阅当前状态 + 订阅历史
```

## 关键决策

- 金额包含货币、最小货币单位和发生时间，禁止使用浮点数保存金额。
- 外部事件 ID 和支付供应商用于幂等与审计。
- MRR 只统计有效经常性订阅，年付按明确规则折算到月。
- 退款、争议、失败、宽限和取消分别建模，不能只依赖当前订阅状态。
- 收入、到账和估算 MRR 在指标名称中明确区分。
- 支付供应商能力不同，由适配器声明可提供的数据和缺口。
- 一个用户只保留一条当前订阅记录；历史变更写入 `subscription_history`。
- 升级立即调用供应商的立即补差价能力，降级先保留当前权益并在下一周期切换。
- 取消默认安排在当前周期结束时执行，周期结束前可以调用恢复接口。
- 订阅 Checkout 使用用户级短期锁和请求 ID；同一价格的有效 Checkout 直接复用。

## 当前实现

`revenue_event` 位于支付 Schema 中，保存供应商、外部事件 ID、交易 ID、事件类型、用户、
订阅、价格、货币、最小货币单位金额、周期和发生时间。`recordRevenueEvent` 使用
`external_event_id + kind` 幂等；有供应商交易 ID 时再用 `transaction_id + kind` 防止同一笔
交易被不同 Webhook 重复入账，并把未配置价格的金额保留为 0，避免把未知值伪装成已确认
收入。

支付 Webhook 已记录 checkout 成功、订阅激活与续费、取消、支付失败和退款。只有被当前
订阅状态机接受的 checkout、激活或续费事件才会写周期收入事实；旧周期事件被忽略时不会
倒灌收入。订阅成功事件使用 `subscriptionId + currentPeriodStart` 作为稳定键，因此
checkout 与 active 重复到达不会重复计入，续费周期变化后会生成新的收入事实。Stripe 的
`invoice.payment_succeeded` 在 `billing_reason=subscription_update` 时会单独记录
`subscription_adjustment`，金额来自 invoice 的真实最小货币单位金额，幂等键来自供应商
交易 ID；补差价收入不参与 MRR。Stripe 已规范化失败支付、退款和补差价事件；Creem
保留相同契约的可选字段。

`subscription` 保存用户当前权益和待生效价格，`subscription_history` 保存创建、升级请求与
确认、降级请求与确认、取消、恢复和续费记录，`subscription_checkout` 保存短期 Checkout 锁。
Action 使用请求 ID，Webhook 使用供应商事件 ID，并通过 correlation ID 关联请求和确认；
重复请求或 Webhook 只保留一条对应事实。数据库同时
对 `subscription.user_id`、Checkout 用户和请求 ID 建立唯一约束。迁移 `0007` 会在建立唯一
约束前按有效状态和最近更新时间保留一条旧订阅记录，避免历史重复数据阻塞升级。

Webhook 每次最多写一条订阅历史，判定顺序如下（`findPendingPlanChangeRequest` 与支付 Webhook
路由）：

1. 取与本次价格对应的最新一条站内改套餐请求：一般按事件价格查找；待生效降级到期被应用时
   按实际生效的价格查找，避免供应商仍报旧价时关联到别的请求。它已经有同方向的确认记录，
   或者没有任何关联编号（早期数据）时，不再算“待确认请求”；更早的请求一律不再参与判定。
2. 当前价格发生变化：有待确认请求写 `upgrade_confirmed` / `downgrade_confirmed`；否则待生效
   价格被应用写 `downgraded`，并关联发起它的降级请求；否则写 `changed`，不带关联编号。
3. 价格未变但有待确认请求：写对应的确认事件。
4. 周期开始时间前进：写 `renewed`。

这样已经确认过的请求不会再拦住之后的续费、降级生效和供应商侧改价（P1-028）。确认事件仍按
`(event_type, correlation_id)` 唯一约束去重。

账单页的取消、恢复订阅按动作返回值判定成败（`resolveSubscriptionActionOutcome`）：只有
`data.success === true` 且没有服务端错误或校验错误才算成功。取消失败时提示失败、确认对话框
保持打开、请求 ID 保留，重试沿用同一 ID，由服务端重放判定和供应商幂等键保证不会重复取消
（P2-019）。

计划变更由 `changeSubscriptionPlan` 校验已登记价格和价格周期。升级使用
`proration-charge-immediately`，降级使用 `proration-none`，Webhook 在下一周期开始时
才把待生效价格写入当前价格。取消和恢复分别调用供应商的 scheduled cancel/resume，删除
账户仍使用 immediate cancel。

运营查询从服务端收入事实聚合周期确认收入、退款、支付失败、周期流失、付费用户与
付费转化率；付费转化率只统计同一注册 cohort 在周期内首次成功的订阅支付，续费和补差价
不进入首次付费分子。只有当前 `active` 订阅按价格配置折算 MRR，`trialing` 不混入经常性
收入，月付按原价、年付按年价除以 12。查询窗口按所选 IANA 时区切日，独立数据源失败时
只将受影响指标标为 `query-failed`，其他指标继续返回。运营页面显示货币、统计周期、时区
和每项数据状态。结果用于运营判断，不代表会计报表。

## 验证方式

- `src/test/operations/revenue.test.ts` 覆盖月付、年付折算、最小货币单位、首购 cohort、
  转化率、空数据和收入源查询失败状态；运营仓储测试覆盖试用订阅不计入 MRR。
- `src/test/adapters/payment.test.ts` 覆盖 Creem checkout、订阅升级、周期末取消、恢复，
  以及 Stripe 订阅项更新、补差价 invoice 和失败支付的统一事件契约。
- `src/test/payment/revenue-history.test.ts` 覆盖补差价交易金额幂等，以及 Action 请求和
  Webhook 确认按 correlation ID 去重。
- `src/test/payment/subscription-change.test.ts` 覆盖升级/降级分类、年付切换和待生效价格
  的周期边界。
- `src/test/payment/subscription-history-webhook.test.ts` 直接调用生产支付 Webhook 路由并连接
  测试数据库，覆盖升级后的逐周期续费、降级确认与生效、供应商当场仍报旧价、同一事件重投、
  供应商侧来回改价、没有关联编号的旧请求，以及待生效降级到期时供应商仍报旧价。
- `src/test/settings/billing-subscription-actions.test.tsx` 与
  `src/test/settings/subscription-action-result.test.ts` 覆盖取消、恢复订阅失败时不提示成功、
  失败重试沿用同一请求 ID，以及动作结果判定规则。
- `src/test/payment/subscription.test.ts`、`src/test/payment/webhook.test.ts` 和
  `src/test/subscription/user-plan.test.ts` 覆盖订阅生命周期、Webhook、取消后权益和用户
  当前计划读取。
- `pnpm db:generate:checked` 已确认 `drizzle/0007_moaning_dragon_man.sql` 与 Schema
  快照一致；Webhook 的事件领取表、订阅历史表和收入表共同保证重放数据可审计。
- 收入读模型只依赖 Webhook 与订阅数据库，不读取浏览器 checkout 事件。
