# 视图契约

> 模块定位：把面向用户的页面拆成“核心负责数据和动作、皮肤负责长相”两半，并用严格类型
> 约定两半之间的接口
>
> 对应代码（规划）：`src/features/<模块>/view/`（视图约定、页面取数、表单逻辑）、
> `src/core/skin/`（公共类型与完整性检查）、`src/core/modules/`（视图登记）、
> `src/app/[locale]/(marketing)/`、`src/app/[locale]/(auth)/`、
> `src/app/[locale]/(dashboard)/`、`src/skin/views/`
>
> 所属里程碑：[M0 - v4.0 基线与前置修复](../roadmap4.x.md#m0)、
> [M1 - v4.1 视图契约与页面拆分](../roadmap4.x.md#m1)
>
> 当前状态：进行中（M0 基线与前置修复）
>
> 最近更新时间：2026-10-22

## 职责与边界

视图契约负责：

- 为 17 个面向用户的页面和三组页面外壳定义视图约定：页面拿到哪些数据、能调用哪些动作、
  必须呈现哪些状态。
- 把路由页面改成薄外壳：会话校验、参数解析、重定向、调用页面取数，再渲染当前皮肤的视图。
- 把表单里的交互逻辑（字段状态、提交、报错、倒计时、第三方登录）抽成无界面的共用逻辑，
  皮肤只负责画。
- 把生成器里按模块拼出的界面代码改成由约定中的可选数据驱动。

视图契约不负责：

- 皮肤包的目录、清单、加载和规矩检查，见[皮肤系统](皮肤系统.md)。
- 管理后台 5 个页面、文档站和演示页的拆分。这些页面保持现有写法，只跟随皮肤的变量层和
  基础组件。
- 任何业务行为、接口、数据库结构或翻译键含义的变化。

## 结构与数据流

```text
请求
  │
  ▼
路由外壳     src/app/[locale]/(分组)/.../page.tsx
  │          会话校验、参数解析、重定向
  ▼
页面取数     src/features/<模块>/view/<页面>.ts
  │          组合本模块和其他模块的查询，返回符合约定的数据
  ▼
皮肤视图     src/skin/views/<模块>/<页面>.tsx
             只接收数据和动作，负责全部界面
             交互 → 本模块的 Server Action 或无界面表单逻辑
```

每个页面的约定包含三部分：

| 部分 | 内容 | 例子 |
|---|---|---|
| 数据 | 页面渲染需要的只读数据，类型由拥有该页面的模块声明 | 控制台首页的用户、当前套餐、积分余额、最近交易 |
| 动作 | 视图可以调用的操作，统一返回成功、失败和错误信息 | 登录、重发验证邮件、提交工单、发起购买 |
| 状态 | 视图必须呈现的状态 | 加载、空数据、错误、成功、提交中、按钮禁用 |

视图约定的形状（示意，以 M1 实现为准）：

```ts
// src/features/dashboard/view/overview.ts
export interface DashboardOverviewData {
  user: { name: string; email: string };
  plan: PlanSummary;
  credits?: CreditsSummary; // 未选择积分模块时不存在
}

export interface DashboardOverviewViewProps {
  locale: Locale;
  data: DashboardOverviewData;
}
```

### 视图归属与裁剪

视图按拥有它的功能模块登记，沿用[模块内核](模块内核.md)的模块声明：每个模块在声明中登记
自己拥有的页面视图和外壳。生成器本来就按模块裁剪路由，未选模块的路由外壳、页面取数、
表单逻辑和皮肤视图会被一起删除。

跨模块的可选数据经模块注册表提供。例如控制台首页属于控制台模块，积分余额和最近交易由
积分模块提供；未选择积分模块时这些字段为空，视图按约定不显示对应区块。

三组页面外壳同样纳入约定：

| 外壳 | 现有组件 | 约定要点 |
|---|---|---|
| 营销外壳 | 页头、导航菜单、页脚、Cookie 提示 | 导航和页脚链接来自核心配置，语言切换和明暗切换由核心提供 |
| 登录外壳 | 品牌区、Logo、页脚 | 品牌名称与 Logo 来自站点配置 |

不纳入整页换皮：管理后台首页、运营驾驶舱、工单管理列表与详情、用户管理，以及文档站和
套餐徽标演示页。

## 关键决策

- 拆分范围限定为营销、登录注册、用户控制台三组共 17 个页面和三组外壳；其他页面保持现状。
- 视图约定、页面取数和表单逻辑放在拥有该页面的功能模块里，随模块一起被生成器裁剪。
- 跨模块数据在约定中是可选字段，视图必须处理缺失；生成器只裁剪数据和动作，不再输出
  界面代码。
- 表单逻辑做成无界面的客户端逻辑，返回字段状态、提交方法、错误和附加动作；校验规则沿用
  现有 Zod 定义，Server Action 沿用现有分级。
- 功能相关文案（表单标签、报错、按钮）继续使用核心的翻译命名空间；皮肤可以带自己的命名
  空间放营销文案。
- 每个视图必须覆盖约定列出的加载、空数据、错误和成功状态。
- 完整性由类型检查保证：皮肤导出的视图集合必须满足所选模块登记的全部视图类型，缺失或
  类型不符时构建失败。
- 拆分不改外观：M1 完成后默认皮肤与 M0 截图基线逐页一致。

## 当前实现

未开始。2026-10-19 只读核查的基线：

- 路由页面共 24 个：营销 7 个（含套餐徽标演示页）、登录 4 个、控制台 7 个、管理后台
  5 个、文档 1 个。
- 6 个页面文件直接查数据库：控制台首页、工单列表、工单详情，以及管理后台首页、工单管理
  列表和详情。
- 登录表单在同一个组件里管理输入、加载、错误和重发验证倒计时，并调用登录函数。
- 生成器在未选择积分或控制台模块时，直接写入精简侧栏、控制台布局和无积分首页的界面代码
  （`packages/create-nextdevtpl/src/generate.ts`）。
- 设置页已经是“服务端取数据、交给客户端视图”的写法，可作为拆分样板。
- 界面颜色基本走主题变量：组件里语义颜色类 802 处，写死的调色板颜色 31 处，全部在邮件
  模板。

## 验证方式

- M0：17 个页面在明暗两种主题、电脑和手机两种尺寸下截图，作为基线保存（浏览器自动化
  优先使用 Edge）；页面清单逐页对照代码核实。
- M1 单元测试：每个页面取数函数（含可选模块缺失）、每套表单逻辑（成功、失败、重复提交、
  倒计时）、视图登记与完整性检查。
- M1 回归：现有测试全部通过；默认皮肤截图与 M0 基线逐页对比无差异；`minimal`、`saas`、
  `ai-saas` 三个预设生成后完成安装、类型检查、测试和生产构建。
- 视图组件本身属于纯展示层，不写单测，由类型检查和截图验收覆盖。
