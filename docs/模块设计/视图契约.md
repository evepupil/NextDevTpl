# 视图契约

> 模块定位：把面向用户的页面拆成“核心负责数据和动作、皮肤负责长相”两半，并用严格类型
> 约定两半之间的接口
>
> 对应代码：`src/features/<模块>/view/`（视图约定、页面取数、表单逻辑）、
> `src/core/skin/`（公共类型与完整性检查）、`src/core/modules/`（视图登记）、
> `src/app/[locale]/(marketing)/`、`src/app/[locale]/(auth)/`、
> `src/app/[locale]/(dashboard)/`、`src/skin/views/`、
> `src/modules/{skin-views,view-data,view-runtime}.ts`；截图基线 `e2e/visual/`（M0 已验收）
>
> 所属里程碑：[M0 - v4.0 基线与前置修复](../roadmap4.x.md#m0)、
> [M1 - v4.1 视图契约与页面拆分](../roadmap4.x.md#m1)
>
> 当前状态：M0、M1 已完成
>
> 最近更新时间：2026-11-06

## 职责与边界

视图契约负责：

- 为 17 个面向用户的页面和三组页面外壳定义视图约定：页面拿到哪些数据、能调用哪些动作、
  必须呈现哪些状态。
- 把路由页面改成薄外壳：会话校验、参数解析、重定向、调用页面取数，再渲染当前皮肤的视图。
- 把表单里的交互逻辑（字段状态、提交、报错、倒计时、第三方登录）抽成无界面的共用逻辑，
  皮肤只负责画。
- 把生成器里按模块拼出的界面代码改成由约定中的可选数据驱动。

视图契约不负责：

- 皮肤包的目录、清单、加载和规矩检查，见[皮肤系统](皮肤系统.md)。
- 管理后台 5 个页面、文档站和演示页的拆分。这些页面保持现有写法，只跟随皮肤的变量层和
  基础组件。
- 任何业务行为、接口、数据库结构或翻译键含义的变化。

## 结构与数据流

```text
请求
  │
  ▼
路由外壳     src/app/[locale]/(分组)/.../page.tsx
  │          会话校验、参数解析、重定向
  ▼
页面取数     src/features/<模块>/view/<页面>.ts
  │          组合本模块和其他模块的查询，返回符合约定的数据
  ▼
皮肤视图     src/skin/views/<模块>/<页面>.tsx
             只接收数据和动作，负责全部界面
             交互 → 本模块的 Server Action 或无界面表单逻辑
```

每个页面的约定包含三部分：

| 部分 | 内容 | 例子 |
|---|---|---|
| 数据 | 页面渲染需要的只读数据，类型由拥有该页面的模块声明 | 控制台首页的用户、当前套餐、积分余额、最近交易 |
| 动作 | 视图可以调用的操作，统一返回成功、失败和错误信息 | 登录、重发验证邮件、提交工单、发起购买 |
| 状态 | 视图必须呈现的状态 | 加载、空数据、错误、成功、提交中、按钮禁用 |

视图约定的形状（示意，以 M1 实现为准）：

```ts
// src/features/dashboard/view/overview.ts
export interface DashboardOverviewData {
  user: { name: string; email: string };
  plan: PlanSummary;
  credits?: CreditsSummary; // 未选择积分模块时不存在
}

export interface DashboardOverviewViewProps {
  locale: Locale;
  data: DashboardOverviewData;
}
```

### 视图归属与裁剪

视图按拥有它的功能模块登记，沿用[模块内核](模块内核.md)的模块声明：每个模块在声明中登记
自己拥有的页面视图和外壳。生成器本来就按模块裁剪路由，未选模块的路由外壳、页面取数、
表单逻辑和皮肤视图会被一起删除。

跨模块的可选数据经模块注册表提供。例如控制台首页属于控制台模块，积分余额和最近交易由
积分模块提供；未选择积分模块时这些字段为空，视图按约定不显示对应区块。

## 关键决策

- 拆分范围限定为营销、登录注册、用户控制台三组共 17 个页面和三组外壳；其他页面保持现状。
- 视图约定、页面取数和表单逻辑放在拥有该页面的功能模块里，随模块一起被生成器裁剪。
- 跨模块数据在约定中是可选字段，视图必须处理缺失；生成器只裁剪数据和动作，不再输出
  界面代码。
- 表单逻辑做成无界面的客户端逻辑，返回字段状态、提交方法、错误和附加动作；校验规则沿用
  现有 Zod 定义，Server Action 沿用现有分级。
- 功能相关文案（表单标签、报错、按钮）继续使用核心的翻译命名空间；皮肤可以带自己的命名
  空间放营销文案。
- 每个视图必须覆盖约定列出的加载、空数据、错误和成功状态。
- 完整性由类型检查保证：皮肤导出的视图集合必须满足所选模块登记的全部视图类型，缺失或
  类型不符时构建失败。

### M1 实施约定

公共接口：`src/core/skin` 只提供通用的 `SkinView`、`SkinViews` 类型，不导入业务模块。
功能模块在公开的 `src/features/<模块>/view/index.ts` 导出自己的 `ViewContracts` 类型，
键为稳定视图编号、值为该视图的参数。此入口可同时导出客户端安全的无界面控制逻辑；服务端
查询通过本模块 `/server` 暴露，不混入客户端入口。参数不得引用数据库行或供应商 SDK 类型。

模块清单通过可选 `views` 数组登记 `{ id, kind }`，编号以所属模块加点号开头，种类为
`page` 或 `layout`。内核检查编号格式、归属和重复登记，选择结果汇总实际选中的视图。

生成器的 recipe 同步登记这些视图，并记录本模块的 `viewContract`、`skinEntry` 和
`skinSources`：前两者是相对仓库根目录的公开类型入口和默认皮肤导出入口，后者是归属本模块
的皮肤目录或文件。路径按现有相对路径规则校验，未选模块的视图、入口和素材一并裁剪。

当前固定的视图编号：

| 归属 | 编号 |
|---|---|
| shared | `shared.dashboard-layout`、`shared.empty-dashboard` |
| auth | `auth.layout`、`auth.sign-in`、`auth.sign-up`、`auth.forgot-password`、`auth.reset-password` |
| marketing | `marketing.layout`、`marketing.home`、`marketing.legal` |
| blog | `blog.list`、`blog.post` |
| pseo | `pseo.list`、`pseo.detail` |
| dashboard | `dashboard.overview` |
| settings | `settings.page` |
| support | `support.list`、`support.new`、`support.detail` |

17 个用户入口中有 2 个积分重定向，没有自己的视图；实际页面视图为 15 个，加 3 个外壳。
另保留 `shared.empty-dashboard` 作为现有生成器无积分首页的兼容回退，不增加可选布局功能。
控制台外壳归属 shared，因为未选择 dashboard 的认证项目仍可能包含设置、工单等受保护页面。

每个 `src/skin/views/<模块>/index.ts` 导出 `views` 对象，并用本模块的契约检查完整性。
`src/modules/skin-views.ts` 汇总所选模块的类型和视图，导出 `skinViews`；缺视图、导出不匹配
或参数不兼容时类型检查失败。生成项目只引用已选模块，核心层不反向引用这些业务类型。

组合层另外提供服务端 `src/modules/view-data.ts` 和客户端 `src/modules/view-runtime.ts`。
它们仅按实际模块选择接入会话、积分和订阅数据或无界面控制逻辑：控制台自己定义可选数据形状，
不静态导入积分或订阅类型；未选功能时既没有导入，也没有对应 UI 区域。控制台外壳通过这个
公开控制入口拿到数据、状态和动作，皮肤仍不直接调用服务或供应商 SDK。

生成器可以继续写运行时装配和薄路由的导入、导出与视图调用，但不再拼 HTML、样式类或默认
侧栏。现有三种外壳条件（无认证的公开主区域、有认证但无 dashboard 的简单主区域、带侧栏的
完整工作区）以及无积分时的标题与副标题回退，统一交给基础皮肤按明确数据渲染。

拆分时保持现有行为：不增加登录回跳处理、不新增第三方登录按钮、不修复设置页标签查询参数，
不顺带调整工单的错误处理或手机端外观。控制台首页读取余额保持无副作用，注册奖励仍由原有
徽标的加载路径触发；账单和用量仍按标签加载。

#### 工作区与可选模块的接线约定

- `shared.dashboard-layout` 只接收 `children` 和 `mode`；模式为 `public`、`protected`、
  `workspace`。前两者保持现有简单主区域，最后一种显示侧栏。真实会话校验和未登录重定向
  仍在路由外壳，不能放入皮肤或 shared 模块。
- 客户端组合入口导出 `useDashboardRuntime()`，返回导航、当前用户、登出操作和能力开关。
  另提供 `useWorkspaceCredits()`、`useWorkspacePlan()`，分别返回本地声明的余额与加载状态、
  套餐标识。选择后的函数只静态导入已选功能的公开控制入口；shared 功能代码不反向导入可选
  功能。皮肤通过这些入口调用公共行为，侧栏折叠、菜单开合等纯界面状态留在皮肤。
- 可选徽标保持独立挂载：用户信息出现后才挂载积分徽标，账号弹出菜单打开后才挂载套餐徽标。
  工作区入口不能提前执行两者的取数逻辑。这样保留原有注册积分检查和套餐请求的触发时机，
  关闭菜单后自然卸载，重新打开仍走原先的初始加载流程。
- 导航图标可以在客户端控制结果中使用组件引用，不从服务端传递函数。跨服务端/客户端传递
  的页面数据只含普通值和明确允许的正文节点，避免把图标或普通回调塞进服务端参数。
- 服务端组合入口提供选中的工作区模式、会话读取和首页可选数据读取。首页数据的拥有者为
  dashboard；积分和订阅提供者通过显式参数接入，dashboard 本身不导入这两个可选模块。
  查询结果先映射为本地声明的余额、交易和套餐摘要，不直接暴露数据库记录。
- 积分徽标与套餐徽标的取数逻辑各归其功能模块的公开控制入口；默认皮肤只负责徽标外观。
  设置页用量、账单表单同样拆成公共控制逻辑与皮肤视图，保持原先按标签挂载的时机。
- 两份视图登记的一致性由仓库测试核对；生成器运行时不加载模板的业务注册表。
  皮肤入口必须处于所属模块登记的皮肤来源范围内。
- 侧栏、简化首页与通用套餐徽标由 shared 提供，其使用的 `Dashboard`、`DashboardPages`、
  `Subscription` 文案也归 shared 登记，防止精简组合保留组件却裁掉所需翻译。
- 交易的收支方向和本地化说明在积分功能层计算。用量视图只接收整理后的说明、金额、日期和
  收支结果，不向皮肤继续传递原始交易附加信息。
- 路由裁剪按文件归属进行，不能因 dashboard 未选而递归删除仍选中的设置或工单页。
  简化首页回退仅在 dashboard 已选且积分未选时启用；未选 dashboard 时不补回该路由。
